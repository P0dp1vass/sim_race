## Как Setup Recommendation Service сопоставляет жалобу с правилом

В MVP нет NLP/ML-компонента (см. [`ml-llm-boundary.md`](ml-llm-boundary.md), KIR-03).
Запрос структурирован, поэтому сопоставление — точное совпадение значений, не текстовый
поиск:

- `symptom_type` и `corner_phase` запроса должны точно совпасть с одноимёнными полями
  правила.
- `stint_moment`: если правило имеет `null` — подходит для любого момента; если у
  правила указано значение — должно точно совпасть со значением запроса (если пилот не
  передал `stint_moment`, такие правила не подходят).
- `car` и `track` должны входить в списки `applicability.car` / `applicability.track`
  правила (проверка на членство в списке, а не на равенство).
- Участвуют только правила со статусом «разрешено к выдаче» (FED-05).
- Поле `comment` в поиске не участвует — оно сохраняется в `requests` как материал для
  ручного анализа (новые кандидаты в правила), не как источник матчинга.

**Риск данных, не моя задача чинить, но блокирует ROD-04/FED-05.** В VAR-04 все пять
правил имеют `applicability.track: []` с пометкой «это не означает применимость ко всем
трассам». По правилу matching'а выше пустой список — это «ни одна трасса не подходит»,
а не wildcard. Значит, пока FED не укажет конкретные трассы в `applicability.track`, эти
правила не совпадут ни с одним запросом, даже если FED-05 переведёт их в «разрешено» —
сервис будет возвращать `no_match` на любое валидное сочетание. Нужно решить это до
ROD-04/ROD-05, иначе тесты AC-02/AC-16 из ALE-02 не пройдут физически ни на одном
правиле.

**Пробел покрытия, тоже не мой fix, но стоит знать.** Cheat sheet FED-04 использует 5 фаз
поворота (торможение, вход, апекс/середина, разгон, выход), а `corner_phase` в контракте
— только 3 (`entry`, `mid`, `exit`, решение ALE-03/VAR-03). Правила для фаз «торможение»
и «разгон» (01, 04, 06, 09 в cheat sheet) нельзя выдать через текущий API, даже если их
одобрят в FED-05, — `corner_phase` для них не из enum. Либо расширять enum, либо явно
не брать эти правила в FED-05.

## POST /api/v1/recommendations

### Запрос

Content-Type: `application/json`

| Поле | Тип | Обязательно | Значения |
|---|---|---|---|
| `car` | string, enum | да | машина из FED-02; в MVP одно значение |
| `track` | string, enum | да | овал из списка FED-02 |
| `symptom_type` | string, enum | да | `understeer` (недостаточная поворачиваемость) / `oversteer` (избыточная) |
| `corner_phase` | string, enum | да | `entry` / `mid` / `exit` |
| `stint_moment` | string, enum | нет | `from_start` / `after_laps`; не передано = любой момент |
| `comment` | string, 3–500 символов | да | проблема своими словами; в поиске не участвует, сохраняется для анализа |

```json
{
  "car": "NASCAR Cup Series Next Gen (Gen 7)",
  "track": "<овал из FED-02>",
  "symptom_type": "oversteer",
  "corner_phase": "exit",
  "stint_moment": "after_laps",
  "comment": "После 5 кругов зад срывает на выходе из 3–4, приходится раньше сбрасывать газ"
}
```

### Ответ 200 — найдено совпадение (`match`)

Не больше 3 рекомендаций; впереди — правила, у которых `stint_moment` совпал с запросом
(решение по вопросу 5 ALE-03).

```json
{
  "status": "match",
  "request_id": "6f1c2a9e-3b7d-4c11-9a0e-2d5b8f7c4e10",
  "recommendations": [
    {
      "rule_id": "R-001",
      "parameter": "давление задних шин",
      "direction": "decrease",
      "change_description": "Снизить давление в задних шинах на 1–2 psi",
      "expected_effect": "Увеличение пятна контакта задней оси, снижение избыточной поворачиваемости на выходе из поворота",
      "limitations": "Не снижать ниже рекомендованного производителем минимума",
      "basis": "VAR-01 / проверено FED-05"
    }
  ]
}
```

Все 7 полей рекомендации обязательны (включая `limitations` и `basis` — в отличие от
версии 1, здесь они не nullable: правило без ограничений и источника не проходит FED-05).

### Ответ 200 — совпадений нет (`no_match`)

```json
{
  "status": "no_match",
  "request_id": "0a8d4e21-7c5f-4b3e-8e19-6b2f1d9c3a77",
  "message": "Подходящее правило не найдено. Попробуйте описать жалобу точнее."
}
```

### Ответ 400 — ошибка валидации

```json
{
  "status": "error",
  "error": {
    "code": "validation_error",
    "message": "Проверьте заполнение полей",
    "fields": {
      "corner_phase": "обязательное поле",
      "comment": "должен содержать от 3 до 500 символов"
    }
  }
}
```

### Ответ 500 — внутренняя ошибка

```json
{
  "status": "error",
  "error": { "code": "internal_error", "message": "Внутренняя ошибка сервера, попробуйте повторить запрос позже" }
}
```

Валидация обязана вернуть **400**, не дефолтные 422 FastAPI — своей структурой тела.
Реализация (`exception_handler`) — ROD-01/03, не меняет контракт, но важно для ROD-05.

## GET /api/v1/recommendations/{request_id}

Возвращает тот же результат, что был выдан на исходный `POST`, чтобы пилот мог вернуться
по сохранённой ссылке из карточки (`/feedback/{request_id}?rule_id=...`, ALE-04) без
опоры на localStorage. Тело ответа — `match` или `no_match`, формат как у `POST`.

- `200` — найден, тело как у `POST /api/v1/recommendations` (`match`/`no_match`).
- `404` — `request_id` не найден: `{"status": "error", "error": {"code": "not_found", "message": "Запрос не найден"}}`.

## POST /api/v1/feedback

Один отзыв — одна применённая рекомендация. `request_id` и `rule_id` frontend подставляет
сам из ответа `recommendations`, пилот их не вводит.

| Поле | Тип | Обязательно | Условие |
|---|---|---|---|
| `request_id` | string (UUID) | да | должен существовать в `requests` |
| `rule_id` | string | да | должен быть среди `recommendations` этого запроса |
| `applied` | enum `as_written` / `other_value` / `not_applied` | да | — |
| `applied_value` | string, ≤200 | если `other_value` | — |
| `not_applied_reason` | enum `unclear` / `no_trust` / `at_limit` / `no_time` / `other` | если `not_applied` | — |
| `symptom_result` | enum `gone` / `weaker` / `same` / `stronger` | если применял | — |
| `new_problem` | boolean | если применял | — |
| `new_problem_text` | string, ≤500 | если `new_problem = true` | — |
| `keep_change` | enum `yes` / `reverted` / `undecided` | если применял | — |
| `clarity` | integer 1–5 | да | — |
| `unclear_text` | string, ≤500 | нет | — |
| `same_conditions` | enum `yes` / `no` / `unknown` | нет | — |
| `conditions_diff` | string, ≤500 | нет | — |

- `201` — `{"status": "ok", "feedback_id": "..."}`
- `400` `validation_error` — не заполнено обязательное поле, неизвестный `request_id`,
  либо `rule_id` не из этого запроса.
- `500` `internal_error`.

## Правила выдачи рекомендаций

- В выборку попадают только правила со статусом «разрешено к выдаче». Непроверенные
  правила backend не возвращает ни при каких условиях.
- Поле `parameter` в ответе использует каноническое русское имя из словаря VAR-02 (71
  уникальный технический параметр), а не произвольную формулировку.
- `rule_id` трассирует рекомендацию до конкретного правила в SQLite.
- `basis` всегда входит в ответ API; показывать ли его пилоту в интерфейсе («Проверено
  экспертом» вместо технического текста) — решение EGO/команды, контракт не меняет.
