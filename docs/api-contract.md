# Контракт API — AI Assistant for Simracing Setups

Задача: KIR-02 — согласовать контракт API.
Статус: согласовано, 13.10.2026. Зависит от [architecture.md](architecture.md) (KIR-01).

Версия: v1. Базовый путь: `/api/v1`. Формат тела запроса и ответа — JSON.

Машиночитаемая версия этого контракта (OpenAPI 3.0, используется для `/docs` и для
генерации Pydantic-моделей в ROD-01): [`openapi/setup-recommendation-service.yaml`](openapi/setup-recommendation-service.yaml).

## Как Setup Recommendation Service сопоставляет жалобу с правилом

В MVP нет NLP/ML-компонента (см. «Вне границ MVP» в [architecture.md](architecture.md) и
границу KIR-03). Сопоставление — поиск по ключевым словам/подстрокам в тексте условия
правила (поле `симптом/условия` из VAR-03), а не семантическое понимание фразы.
Это сознательное ограничение MVP: при 5 правилах (FED-04) оно работает достаточно
точно, при росте базы правил потребуется пересмотреть подход (ML/LLM-граница — KIR-03,
Could have).

## GET /health

Назначение: проверка, что Setup Recommendation Service запущен и отвечает.

Запрос: без тела.

Ответ `200 OK`:
```json
{ "status": "ok" }
```

## POST /api/v1/recommendations

Назначение: принять жалобу пилота и вернуть рекомендации по изменению сетапа на
основе разрешённых к выдаче экспертных правил.

### Запрос

Content-Type: `application/json`

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `symptom` | string | да | Жалоба пилота в свободной форме, 3–500 символов. Участок трассы и фаза поворота указываются внутри текста жалобы, отдельного поля под них в MVP нет. |

Пример запроса:
```json
{
  "symptom": "на выходе из поворота машину уводит в избыточную поворачиваемость"
}
```

Намеренно не добавлены поля `section`/`notes` и т.п.: ни в шаблоне правила (VAR-03:
`симптом/условия, параметр, изменение, эффект, ограничения, применимость, статус`),
ни в сценарии ALE-01 такие поля не фигурируют. Добавлять их раньше, чем появится
обоснованная потребность в VAR-03/ALE-01, — это лишняя сложность контракта.

### Ответы

#### `200` — найдено совпадение

```json
{
  "status": "match",
  "recommendations": [
    {
      "rule_id": "R-001",
      "parameter": "давление задних шин",
      "direction": "decrease",
      "change_description": "Снизить давление в задних шинах на 1–2 psi",
      "expected_effect": "Увеличение пятна контакта задней оси, снижение избыточной поворачиваемости на выходе из поворота",
      "limitations": "Не снижать ниже рекомендованного производителем минимума",
      "basis": "VAR-01 / проверено FED-05"
    }
  ]
}
```

По критериям приёмки (Job Story 1) backend должен вернуть минимум 2 рекомендации,
если база правил позволяет закрыть жалобу несколькими способами.

#### `200` — совпадений нет

```json
{
  "status": "no_match",
  "message": "Подходящее правило не найдено. Попробуйте описать жалобу точнее."
}
```

Backend обязан вернуть `no_match`, а не выдуманную рекомендацию, если в базе нет
подходящего проверенного правила — в том числе пока VAR-04 не заполнена.

#### `400` — ошибка валидации запроса

```json
{
  "status": "error",
  "error": {
    "code": "validation_error",
    "message": "Поле symptom обязательно и должно содержать от 3 до 500 символов",
    "fields": { "symptom": "обязательное поле" }
  }
}
```

#### `500` — внутренняя ошибка сервера

```json
{
  "status": "error",
  "error": {
    "code": "internal_error",
    "message": "Внутренняя ошибка сервера, попробуйте повторить запрос позже"
  }
}
```

## Правила выдачи рекомендаций

- В выборку попадают только правила со статусом «разрешено к выдаче» (проверено
  экспертом, FED-05). Непроверенные правила backend не возвращает ни при каких условиях.
- Поле `parameter` в ответе использует каноническое имя параметра из единого словаря
  (VAR-02), а не произвольную формулировку.
- Поле `rule_id` позволяет трассировать рекомендацию до конкретного правила в SQLite
  (см. схему `rules` в [architecture.md](architecture.md)).

## Связанные задачи

- Схема и источник данных для ответа: VAR-03 (шаблон правила), VAR-04 (набор правил).
- Подробная документация контракта для команды: ALE-03.
- Реализация endpoint: ROD-01, ROD-03, поиск правил — ROD-04.
- Тесты контракта (health, валидный запрос, невалидные поля, `no_match`, скрытие
  непроверенного правила, разрешённое правило): ROD-05.
- Поля формы frontend сопоставляются с этим контрактом в EGO-01.

## Как повторить/обновить

Контракт зафиксирован на основе реестра задач спринта 1 (12–18.10.2026, `planning/`).
Любые изменения полей согласовывать с ALE-03 (документация контракта) и VAR-03 (схема
правил); при breaking change повышать версию (`/api/v2`). Этот файл и
`openapi/setup-recommendation-service.yaml` — одна и та же версия контракта в двух
форматах (для чтения и для `/docs`/кодогенерации); при любом изменении полей править
оба файла в одном коммите.
