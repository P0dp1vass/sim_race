# Архитектура MVP — AI Assistant for Simracing Setups

Задача: KIR-01 — зафиксировать архитектуру MVP.
Статус: согласовано, 13.10.2026.

## Контекст

MVP принимает от пилота текстовую жалобу на поведение машины, сопоставляет её с базой
экспертных правил и возвращает конкретную, проверяемую рекомендацию по изменению
параметра сетапа. MVP работает для одного заранее выбранного автомобиля и овальных
трасс iRacing (см. FED-02).

## Компоненты и границы

### Frontend
- Веб-форма: пилот вводит жалобу на поведение машины и (опционально) участок трассы,
  к которому она относится.
- Состояния интерфейса: загрузка, рекомендация найдена, совпадений нет, ошибка запроса.
- Компонент рекомендации: отображает параметр, направление изменения, ожидаемый эффект
  и ограничения — всё, что пришло в ответе backend.
- Frontend не хранит данные и не содержит логику подбора рекомендаций — только
  валидация формы перед отправкой и отображение ответа backend.
- Общение с backend — исключительно через контракт `POST /api/v1/recommendations`
  и `GET /health` (см. [api-contract.md](api-contract.md)).

### Backend (FastAPI)
- Единая точка входа для рекомендаций: `POST /api/v1/recommendations`.
- Валидирует входящий запрос по контракту (обязательные поля, допустимая длина текста).
- Сопоставляет жалобу с условиями экспертных правил, хранящихся в SQLite.
- Перед сравнением исключает из выборки правила, не прошедшие проверку (статус отличен
  от «разрешено к выдаче», см. FED-05) — непроверенное правило не может попасть в ответ
  ни при каких условиях.
- Возвращает один из трёх исходов: совпадение (одна или несколько рекомендаций),
  отсутствие совпадения, ошибка.
- Не генерирует рекомендации произвольно (ML/LLM) — в MVP только детерминированный
  поиск по базе правил; граница с возможным ML/LLM-слоем зафиксирована отдельно в KIR-03.
- `GET /health` — проверка, что сервис запущен и отвечает.

### SQLite
- Источник истины для параметров сетапа и экспертных правил, backend только читает из неё.
- `parameters`: id, каноническое имя (единое по VAR-02), единица измерения, описание
  влияния на поведение машины, диапазон/ограничения.
- `rules`: id, симптом/условие, ссылка на `parameter_id`, направление изменения, эффект,
  ограничения, применимость, статус проверки, основание/источник.
- Наполняется командой данных по задачам FED-02…FED-05 и VAR-02…VAR-04.

## Поток данных (happy path)

1. Пилот вводит жалобу в форме на frontend.
2. Frontend отправляет `POST /api/v1/recommendations` с телом запроса.
3. Backend валидирует запрос; при нарушении контракта — возвращает ошибку 400.
4. Backend ищет в SQLite правила, условие которых соответствует жалобе, среди правил
   со статусом «разрешено к выдаче».
5. Если совпадений нет — backend возвращает ответ `no_match`.
6. Если совпадения есть — backend формирует список рекомендаций (параметр, направление,
   эффект, ограничения) и возвращает ответ `match`.
7. Frontend показывает результат: компонент рекомендации, сообщение об отсутствии
   совпадения или сообщение об ошибке.
8. Пилот проверяет рекомендацию в симуляторе (вне границ MVP-сервиса).

## Ответственность компонентов

| Компонент | Отвечает за | Не отвечает за |
|---|---|---|
| Frontend | форму ввода, состояния UI, отображение рекомендации | подбор правил, хранение данных, бизнес-логику |
| Backend (FastAPI) | валидацию запроса, поиск правил, формирование ответа, `/health` | генерацию произвольных советов, редактирование содержимого правил (только чтение) |
| SQLite | хранение параметров и правил, статус проверки каждого правила | сопоставление жалобы с правилом (это логика backend) |

## Вне границ MVP

- Аутентификация и профили пользователей.
- Генерация рекомендаций через ML/LLM — возможный предмет отдельного решения, граница
  описана в KIR-03.
- Хранение истории запросов пилота сверх того, что нужно для формы обратной связи
  (ALE-04/ALE-05) — обсуждается отдельно, не предполагается по умолчанию в MVP.
- Поддержка нескольких автомобилей/трасс одновременно — MVP ограничен одним
  автомобилем и овальными трассами (FED-02).
