# Архитектурные решения — сравнение вариантов

Цель документа — честно разделить три категории: что уже зафиксировано реестром задач
спринта 1 и не предмет выбора сейчас; что решили мы сами в KIR-01/KIR-02 и могли решить
иначе; что до сих пор открыто и не стоит решать молча за команду.

## Что не является открытым решением

- **FastAPI** — задан реестром задач (ROD-01 «Поднять базовый FastAPI-проект»), выбор
  сделан раньше KIR-01. Сравнивать с Flask/Django сейчас — тратить время спринта без
  практического выбора: менять фреймворк значило бы переписывать уже согласованный
  ROD-01…05.
- **SQLite как БД для MVP** — тоже задан прямо (KIR-01, ROD-02).
- **Доступ к SQLite через SQLAlchemy** — решено (ADR 1), не предмет дальнейшего
  обсуждения в рамках этого спринта.

## ADR 1 — Доступ к данным: SQLAlchemy (решено, не открытый вопрос)

**Статус: принято.** Зафиксировано в [`architecture.md`](architecture.md#sqlite-доступ-через-sqlalchemy-orm):
доступ к SQLite — только через модели SQLAlchemy, сырые `sqlite3`-запросы в проекте не
используются. Таблица ниже — сравнение, на основании которого принято решение, не
список вариантов на выбор.

| Вариант | Плюсы | Минусы |
|---|---|---|
| raw `sqlite3` (stdlib) | ноль зависимостей, полный контроль над SQL | нужно вручную параметризовать запросы (риск SQL-инъекции при небрежной сборке), вручную маппить строки в объекты, схема легко расходится с VAR-03 при правках |
| **SQLAlchemy ORM — выбрано** | параметризация запросов из коробки, модели — единый источник схемы, стандартная связка с FastAPI, миграция на Postgres почти бесплатна при росте базы | +1 зависимость, небольшой порог входа, миграции схемы (Alembic) — отдельный вопрос, который придётся решать отдельно, если понадобится |
| Peewee / Tortoise ORM | легче SQLAlchemy по API | меньше распространены в связке с FastAPI, не видно выигрыша против SQLAlchemy, который оправдывал бы ещё один инструмент |

ROD-02 и так формулирует задачу как «создать SQLite и **модели** параметров/правил» —
ORM предполагался по факту формулировки, а не придуман задним числом. Пример моделей
(`Parameter`, `Rule`) — ветка
[`feature/sqlalchemy-data-layer`](https://github.com/P0dp1vass/sim_race/tree/feature/sqlalchemy-data-layer)
(`backend/app/models.py`, `database.py`, `init_db.py`): это справочный пример схемы для
ROD-02, а не моя реализация этой задачи — сам ROD-02 (endpoint'ы, поиск правил,
наполнение базой) вне моего скоупа (KIR-01/02).

Риск, который стоит держать в голове и которого не было в исходном architecture.md:
пока FED/VAR правят SQLite-файл руками, а backend читает его через SQLAlchemy engine,
параллельная запись может дать `database is locked`. Для Sprint 1 это не критично (правок
немного, не одновременно с демо backend), но стоит явно договориться — не редактировать
файл БД, пока локально запущен сервер, либо гонять правки через `init_db.py`/сид-скрипт.

## ADR 2 — Алгоритм сопоставления жалобы с правилом (обновлено 16.10, статус изменился)

**Статус: решено по-другому, чем 23.09/13.10.** Исходная версия этого ADR сравнивала
варианты текстового поиска (подстрока vs fuzzy vs эмбеддинги) для свободного поля
`symptom`. 15.10 на обсуждении с Алёной (ALE-01/ALE-03) запрос стал структурированным:
`symptom_type`, `corner_phase`, `stint_moment` выбираются из списков кнопками, а не
пишутся текстом. Это закрывает именно тот риск, который раньше был отмечен как
критическая оговорка — не нужен ни fuzzy-matching, ни эмбеддинги, потому что сравнивать
стало нечего: это точное совпадение enum-значений, а не текста.

| Вариант | Плюсы | Минусы | Актуален для Sprint 1 v2? |
|---|---|---|---|
| **Точное совпадение структурированных полей — выбрано** | детерминированно, 0 промахов из-за формулировки, просто тестировать (ROD-05), не требует зависимостей | пилот ограничен списком `symptom_type`/`corner_phase`, не опишет нестандартный случай полем для матчинга | да |
| Подстрока/ключевые слова по `symptom` (решение v1, больше не действует) | ноль зависимостей | не находит синонимы/опечатки, хрупко при росте базы правил | нет — поле `symptom` убрано из контракта |
| Fuzzy-matching (rapidfuzz/thefuzz) | терпимо к опечаткам в тексте | не нужен для enum-полей; обязательные поля и так не ошибаются в написании | нет, предмет снят |
| Эмбеддинги / семантический поиск | находил бы смысловые совпадения в тексте | не нужен для enum-полей; к тому же нарушает границу KIR-03 | нет |
| Генерация совета LLM | максимальная гибкость формулировок | прямо запрещено ROD-04 («не выдумывать совет») | нет |

**Что осталось нерешённым, несмотря на структурированный ввод** — см.
[`ml-llm-boundary.md`](ml-llm-boundary.md) (KIR-03): cheat sheet FED-04 даёт больше
кандидатов, чем 5 правил VAR-04, но большинство — `direction: conditional`, зависят от
данных, которых структурированный запрос не собирает (температуры шин и т.п.). Это не
повод возвращаться к тексту/ML — это пробел в полях ввода, а не в алгоритме поиска.

**Свободный текст не исчез, сменил роль.** Поле `comment` в запросе обязательно, но в
поиске не участвует — это лог для ручного анализа (FED/Алёна ищут кандидатов в новые
правила), не входная точка матчинга. Если это когда-нибудь изменится — см.
`ml-llm-boundary.md`, это прямой ML-триггер.

## ADR 3 — Один сервис vs несколько

Решение не изменилось: один backend-процесс (Setup Recommendation Service), не
микросервисы за шлюзом. Полное обоснование и альтернатива на будущее — в
[`architecture.md`](architecture.md#выделение-сервисов), здесь не дублируется.

## Открытые вопросы — не решаем их за команду

- **Frontend-фреймворк.** EGO-01 ссылается на «существующий макет», но реестр задач не
  называет технологию (vanilla JS? React? что-то третье?). Это прямо влияет на оценку
  EGO-01…04 (1+2+3+2 SP), но не относится к KIR-01/02 — команде стоит явно
  зафиксировать выбор, а не оставлять по умолчанию.
- **CORS между frontend и backend.** Больше не бесхозный пробел: ALE-03 (15.10) сама
  подняла этот же вопрос как «вопрос 8» и назначила его Родиону/Егору. Решение здесь не
  нужно — только подтверждение, что он взят в работу.
- **Хостинг/деплой** — вне Sprint 1, уже отмечено в «Вне границ MVP» `architecture.md`,
  здесь не повторяется.

## Вывод

Из всего, что можно было пересмотреть в рамках KIR-01/02, оправданной оказалась одна
замена — SQLAlchemy ORM вместо сырых `sqlite3`-запросов; решение принято и зафиксировано
в `architecture.md` (ADR 1), пример моделей — в `feature/sqlalchemy-data-layer` (сейчас
отстаёт от схемы v2, нужно обновить под `requests`/`feedback`, когда до этого дойдёт
очередь). Сервисная граница (ADR 3) не менялась. Алгоритм сопоставления (ADR 2)
пересмотрен не мной, а решением 15.10 с Алёной — структурированный ввод закрыл риск,
который раньше был открытой оговоркой; граница с ML/LLM вынесена в отдельный документ
[`ml-llm-boundary.md`](ml-llm-boundary.md) (KIR-03), так как переросла рамки одной
таблицы сравнения.
Frontend-стек — всё ещё открытый пробел реестра задач. CORS — больше не пробел, взят в
работу ALE-03/ROD/EGO.
